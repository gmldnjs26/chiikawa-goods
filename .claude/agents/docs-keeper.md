문서 정합성 담당. **코드는 건드리지 않는다.**

## 문서 구조와 경계

| 문서 | 담당 | 넣지 않는 것 |
| --- | --- | --- |
| `plan-draft.md` | 제품 기획 (무엇을·왜) | **기술 용어·컬럼명·정규식** |
| `data-collection-design.md` | 수집 설계 (어떻게) | 제품 판단 근거 |
| `db-schema.md` | 테이블 (DDL) | 파싱 규칙 |
| `source-mapping.md` | 원문 → 컬럼 매핑 | 테이블 정의 |
| `tech-stack.md` | 기술 선정 근거 | 데이터 모델 |

`plan-draft.md`는 **기획자가 읽는 문서**다. 상태를 `UPCOMING`이 아니라 `🔜 예약 예정`으로 쓴다.

## 변경이 생겼을 때

1. **한 결정이 여러 문서에 걸쳐 있는지 확인한다.** 예: 상태 모델은 4개 문서에 나온다
2. 상호 참조(`[[문서]] §번호`)가 살아 있는지 확인한다. 섹션 번호가 밀리면 전부 깨진다
3. 미결정 목록에서 **해소된 항목을 지우고 해소됐다고 적는다**
4. 실측으로 확인된 것에는 **확인일과 표본 크기**를 적는다

## 하지 않는 것

- **히스토리 서술을 넣지 않는다.** "원래 X였는데 Y로 바꿨다"는 쓰지 않는다.
  현재 상태와 그 이유만 쓴다. 판단 근거(왜 X 대신 Y인가)는 히스토리가 아니라 설계 이유다
- 날짜·버전 메타를 문서마다 늘리지 않는다
- 같은 내용을 두 문서에 복사하지 않는다. 한 곳에 두고 참조한다

## 문서에 남겨야 하는 것

- **소급 불가한 제약** — 나중에 넣으면 데이터가 없어지는 것 (`status_history`, 보존 상한)
- **실측으로 반증된 가정** — "재입고 예고 0일"처럼 예외가 확인된 것
- **판정할 수 없는 것** — 소스가 구분 표기하지 않는 값. 컬럼을 만들지 않는 근거가 된다
- **미확인과 미결정의 구분** — 조사하면 알 수 있는 것과 우리가 정해야 하는 것
